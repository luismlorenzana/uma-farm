Architecture

How uma-farm is built and run. The game's rules are in the game mechanics document. Every cloud value (the project, the services, the database, the buckets, the accounts and their roles) is in infrastructure.md, the one place to read or change them.

The rules of the codebase

  • The domain decides. The web app runs the rules locally for instant play. The API parses every upload with the same code and refuses one it can't read.
  • The server never writes into a save. It stores what the app sent, or refuses it and keeps it aside. A new farm over an older save is made in the app.
  • Nothing is imported from the other Uma games. A few pieces were copied from uma-rpg at a recorded commit (30a322a) and are owned here, each saying so at its top: the save's envelope and conflict rule, the device store, its sync and Dexie, the API client, the API's save and push modules, and the save's rule errors. uma-rpg's work engine is gone.
  • Original-game content never goes in git. Master data arrives at runtime from uma-platform's private release; the story pack lives in the ignored content/ folder and a private bucket; test fixtures come from @luismlorenzana/uma-data/testing. scripts/check-private-content.test.mjs runs in CI.

State

  • The save store (src/save/game.ts): a Zustand store, useGame, holding the uid, the boot status, the save, its server revision, whether it's dirty, the sync state, the last good sync and when a newer save last replaced local changes.
    • Every change goes through commit(save): the store, then the device, then a sync 1.5 s later. commit never stamps account.updatedAt; a player's action stamps it with touched.
    • madeHere(save) says whether a save is the one this device's last commit made. The HD-2D stage walks the Umas for those, and places everyone at once for any other.
  • Boot (boot(uid)) waits for the story pack, then opens the device save, else the server's, else starts a new farm (newSave), and resolves { startOver }:
    • a v4 plays as it is;
    • a save older than v4 (read as its version and account) stops at uma-kit's first-launch step, the start-over card (app/StartOverCard.tsx), with nothing written; its button (startOver) keeps a dirty device save as a wiped safety copy (the raw row, readStoredRow), then commits freshV4, unstamped, so it uploads and the next boot reads v4;
    • a save newer than v4 throws NEWER_SAVE_WORDS (below).
  • What a sync plays (playable): a v4 as it is, an older save as the same fresh v4 (uploaded on the next pass), a newer one refused before any upload.
  • Sync (syncNow, reconcile.ts): one pass reads GET /api/save, then reconcile decides to adopt, push or do nothing; a push sends PUT /api/save with its base revision, and a 409 reconciles against the stored envelope it carries, up to three times a pass. Passes coalesce, and a change made during one runs another. Triggers: a commit (1.5 s later), the page becoming visible, the network returning, and boot with a device save. The player-facing rules are in the mechanics document's save section.
  • Master data (src/master/master.ts): a small external store read with useSyncExternalStore: the release's manifest, the album's rows of every outfit with a stable id, stats, birthdays and the art index, through the content client from /api/master, seen through the story pack's cast once it loads.
  • The story pack (src/story/story.ts): loaded once, by boot. outfitFor resolves a roster key (a character id) to her outfit.
  • Device preferences go through uma-kit's prefs under the farm. prefix (the appearance, farm.stage). The story's last good index is farm.story-index in localStorage.

Dexie

Database uma-farm, schema version 1, loaded on demand when device I/O starts.

TableKeyRow
saveid, always main{ uid, revision, save, dirty, lastSyncedAt }: the whole save as stored, the server revision it's based on (0: never synced), whether it changed since the last good sync, and when the server last held everything
safety++id, indexed by uid{ uid, reason, at, revision, save }, reason replaced, restore, unreadable or wiped; the newest five per account
  • A row for another uid is never read.
  • A row that can't be parsed is kept as an unreadable safety copy, and boot reads the server's save.
  • Nothing replaces unsynced changes without a safety copy: if the copy can't be written, the adopt doesn't happen.
  • Where IndexedDB is unavailable (private mode), the store still holds the save and sync still backs it up.

The API

  • apps/api/src/main.ts: global prefix /api, JSON bodies up to 1 MB, CORS for ALLOWED_ORIGIN (default http://localhost:5194; production is same-origin through Hosting), listening on PORT (8080; 8101 on the dev server).
  • app.module.ts: config, the owner guard, the master data proxy, the story pack's route, the save and push modules, and the health and ping controllers.
  • Persistence: PERSISTENCE=firestore uses the Firestore database FIRESTORE_DATABASE (default farm); anything else uses a local file for saves and memory for push.

The owner guard

uma-server's AuthModule, applied to every route: - a Firebase ID token (Authorization: Bearer …) whose email is ALLOWED_EMAIL (any case) gets in, as the token's uid; - no token, or an invalid one: 401. A valid token for anyone else, or no ALLOWED_EMAIL set: 403; - AUTH_MODE=disabled lets every request in as the uid local-dev, without calling Firebase; - @Public() routes skip it: health, the parcel ping and the push tick, which check their own tokens. The master and content controllers also carry the guard themselves, so neither can go out unguarded.

Push, and its paused scheduler

The push routes work, but nothing uses them: days are turns, so nothing finishes while the app is closed. The web app sends no subscription and no schedule, and Account's Notifications card says "Off: days are turns". The Cloud Scheduler job that calls the tick every five minutes is paused. The routes, the service worker's handlers and the job stay in place, so notifications can come back without new plumbing.

  • The keys: VAPID_KEYS ({ publicKey, privateKey }, from Secret Manager in production). Without them push is off: the key route answers 404 and nothing sends.
  • The tick's guard (SchedulerGuard): a Google-signed OIDC token for PUSH_AUDIENCE from the scheduler's account (PUSH_SCHEDULER_EMAIL overrides the default). No token, a bad one, or no audience set: 401. Any other account: 403. Nothing lets an unsigned tick in, locally either.
  • The tick: for each account with a subscription, every schedule entry due since its last send (six hours back at most) becomes one "Work done" notification, a line per place, sent to every device. A device that answers 404 or 410 is dropped. It writes only when it sent something or a device was gone.
  • The schedule's places are the farm's nine work places (isPushPlace), at most 36 entries (PUSH_SCHEDULE_MAX, one a slot); one place's notice opens its quick look (/?peek=<place>).

The save on the wire

Documents

DocumentFieldsWritten
saves/{uid}revision; save, as JSON text (Firestore refuses a list inside a list); updatedAt, the server's timeEach accepted upload, in a transaction
saveBackups/{uid}-v{n}The stored saves/{uid} document as it was, whole, and backedUpAtIn the same transaction, when an upload's version is higher than the stored version n: the first v4 over an older save backs that one up (saveBackups/{uid}-v3 for the owner's)

Locally the saves are one JSON file, apps/api/.data/save.json (LOCAL_SAVE_FILE moves it): { [uid]: { revision, save } }, written atomically (a temporary file, then a rename) with calls serialized. A refused upload goes to save.json.rescue.json beside it (the newest only). There are no backups locally, and push lives in memory.

Revisions and refusals

  • GET /api/save returns the stored save parsed (parseStored): a v4 whole, a save from before v4 as its version and account only (the rest stays in the document, unread).
  • PUT /api/save takes exactly { baseRevision, save }. The API parses the save strictly as v4 (parseSavePut) and checks that save.account.uid is the caller's. It stores the save as baseRevision + 1 when the stored revision is baseRevision and the save's version isn't older than the stored one, and answers the new envelope.
  • A 409 carries { message: 'revision conflict', current }, the stored envelope, so the app can reconcile and retry.
UploadAnswerKept in saveRescues
Accepted200, the new envelope—
Stale revision, same or newer version409 with currentNo: the app just syncs again
A version older than v4 (an old cached build's)400, "expected 4"Yes: it may hold play that can never be uploaded

A save the parse refuses (shape, unknown keys, ids, a newer version)400, with the failing pathYes
Another account's save400Yes

A rescue that fails to write is logged and never hides why the upload was refused.

Versions

VersionWhatWho writes it
1–3Older formats, from before the farm started overNothing: read as { version, account } (OlderSave)
4The farm: the farmer's name, the loop, love, the homestead, memories, arrivals, rosters keyed by character idThe app (SAVE_VERSION)
  • parseSave (packages/domain/src/save/save.ts) parses a v4 strictly (parse-v4.ts, with parse-loop.ts's parts): unknown keys and bad ids are refused, each error with its path (SaveParseError). It refuses any other version: what an upload must be. parseStored reads what's stored, on the server or the device: a v4 by parseSave, a v1–v3 as its version and account only, a newer one refused.
  • The new farm runs in the app, never on the server: freshV4 (save/v4.ts) makes day 1 on v4 with account copied whole, committed unstamped, so it uploads with updatedAt unchanged and the next boot reads v4; a dirty device save it replaces is kept first as a wiped safety copy.
  • v4 grows in place while the game is being built; a shape old fields can't carry is v5, with a migration or a new start.
  • Only a player's change moves account.updatedAt (touched). The conflict rule (resolveConflict) compares it: the newer wins whole, a tie keeps the device's.
  • The production-save rules: never move save.account.updatedAt by hand; no server ever writes into a save; a stale server date means stop and ask the owner.

The newer-save refusal

An old client never half-reads or overwrites a newer save: - The parse refuses a version above SAVE_VERSION, on the server (a 400, rescued) and on the device (the row is kept as an unreadable safety copy and boot reads the server's). - A newer server save: boot throws NEWER_SAVE_WORDS, so it stops on uma-kit's gate with "This save is from a newer version of the farm." and Try again; Root.tsx asks the service worker for an update at once, so the update prompt comes up. A sync that meets one stops before any upload. - The server refuses an upload older than the stored version (a 409, rescued).

The story pack's delivery

The game's story is a private pack: never in git, never in the bundle.

  • The source is the ignored content/story/ on the author's Mac.
  • pnpm story:release (scripts/story/release.mjs; Node 22.18 or later, for type stripping) reads the pack with the game's own reader (readStoryPack, read in place). Any pack releases: an error (only what the game can't read) skips the one part it's in, notes block nothing, and both are printed; it refuses only a missing pack folder. The release holds the pack as the game reads it (the menu). It writes the ignored content/story-release/, laid out as the bucket is: the index story.json (each file's path, bytes and SHA-256) and each file minified as story/<name>.<hash8>.json. The same inputs give the same files, and only the pack's own files are read. --stand-in releases the invented stand-in in git, for the dev server; --from <dir> --out <dir> moves both ends. Tests: scripts/story/release.test.mjs.
  • pnpm story:publish (scripts/story/publish.sh) runs the release, then uploads the hash-named files first (gcloud storage rsync, private, max-age=31536000, immutable) and story.json last (private, no-cache), so a reader never sees an index pointing at missing files. Old files stay, so a phone holding an older index still reads it, and the bucket's versioning keeps older indexes. It scopes every gcloud call by the environment and never changes the account. --dry-run lists what it would upload. The bucket is gs://uma-farm-content, or $STORY_BUCKET.
  • The route (apps/api/src/story/story-pack.ts): uma-server's PrivatePackModule at /api/content/, behind the owner guard. It serves an allowlist only, story.json and story/<name>.<hash8>.json: the index revalidated on every read (private, no-cache), the hash-named files cached for good. It reads STORY_BUCKET when that's set and not empty, else STORY_DIR (default the repo's content/story-release/); with neither, every path answers 404.
  • The loader (apps/web/src/story/load.ts, delivery.ts), by boot:
    • story.json fresh from the server through uma-kit's content client;
    • offline or failing, the last good index from localStorage (farm.story-index, a few KB of ids and hashes, never a line of the story); with none, the load throws and the boot gate offers Try again;
    • each file by its path, verified against the index's hash and kept in the content client's Cache Storage, so it downloads once: the cast, the ties, the bibles and the household at boot, routes and pairs on demand;
    • each file read with the same reader, a part with an error skipped; only a hash that doesn't match, or a route or pair that isn't what the index lists, fails the load;
    • the index is kept on the device only once the pack it names has loaded;
    • on the dev server only, a 404 for story.json (farm-api serves no release) plays the invented stand-in, and VITE_FARM_STORY=stand-in forces it. DEV_ONLY_MODULES keeps the stand-in out of every production build.

Lists in the mechanics document that come straight from the rules are rendered from the code, so they can't drift.
